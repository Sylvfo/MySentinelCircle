MY SENTINEL CIRCLE — DATABASE DRAFT (raw brainstorm, to be reconciled with
plan.txt's DATA MODEL sketch)
===========================================================================

Ceci est une premiere passe de mise en forme des champs bruts. Rien n'est
encore un schema Prisma final — objectif : lister les champs, les regrouper
par entite, et flaguer ce qui est nouveau par rapport a plan.txt.

USER (compte / personne)
---------------------------
- id
- is a ME (with a paid account + a son propre cercle en tant que "Me")
- is only a sentinel with an account (can chat)
- is only a sentinel without account (only name, number registred and agreement?)

- nom, prenom
- adresse
- langue
- donnees facturation                (abonnement/paiement — a definir)
- assurances                          (police(s) d'assurance liee(s))
- mineur ou majeur                    (impact legal : consentement parental
                                        pour un compte mineur ?)
-si mineur, responsable légal(parents...) plusieurs champs...

  -> un meme compte peut cumuler les deux, comme dans plan.txt (un
     Companion est le "Me" de quelqu'un d'autre).
- mort                                (personne decedee — impact : que
                                        devient le compte/l'historique ?)
- alertes en cours                    (derive : alertes actives le
                                        concernant)
- historique des alertes              (derive : log complet, cf. entite
                                        Alerte)

NOTE : correspond a peu pres a "User" + "Contact" dans plan.txt. A trancher :
les champs sensibles (assurance, mort) vont sur le compte User
directement, ou sur un profil separe avec acces plus restreint ?

LIEN (Me <-> Sentinel, dans un Circle)
----------------------------------------
- id
- Me ou Sentinel                      (qui est qui dans la relation)
- nom du cercle
- ordre dans le cercle                (tier — determine qui recoit
                                        l'alerte en premier / peut escalader)
- statut : en attente / valide par les deux / refuse
  -> qui doit valider dependant de qui a initie le lien (cf. plan.txt :
     initiatedBy me | sentinel)
- sentinel ou sentinel+
- organisation ??                     (le lien est-il rattache a une
                                        Organization plutot qu'a un
                                        individu ? ex : personnel d'un
                                        hotel devenant Sentinel temporaire)
- duree du lien                       (NOUVEAU — lien a expiration, ex. 1
                                        semaine pour un sejour a l'hotel ;
                                        n'existait pas encore dans plan.txt)
- historique (alertes, reponses, messages)  (derive : cf. AlertNotification
                                              + Message dans plan.txt)

NOTE : correspond a "CircleMembership" dans plan.txt. Le champ "duree du
lien" introduit un nouveau concept : des liens Sentinel temporaires/
expirables, utile notamment pour les Organizations (hotel, camp...) qui
veillent sur quelqu'un le temps d'un sejour plutot qu'indefiniment.

ALERTE
-------
- id
- concerne qui                        (personne visee par l'alerte)
- date / heure
- lancee par qui                      (toujours un Sentinel, jamais le
                                        Companion lui-meme ; ou Organization,
                                        authentifiee via l'app)
- pourquoi                             (motif de l'alerte, texte libre —
                                        deja integre dans plan.txt :
                                        Alert.reason)
- qui a ete contacte                   (inclut toujours le "Me" concerne
                                        directement, pas seulement son
                                        cercle — deja integre dans plan.txt)
- qui a repondu
- prise de controle par le "Me"       (le "Me" concerne peut reprendre la
                                        main sur l'alerte a tout moment,
                                        ex. se marquer en securite / la
                                        cloturer lui-meme — deja integre
                                        dans plan.txt : Alert.resolvedBy)
- historique des echanges             (cf. Message)
- fermee ou non
- si la personne concernee est ok avec ca   (NOUVEAU — confirmation a
                                        posteriori par la personne visee
                                        que l'alerte etait justifiee/
                                        acceptable)
- si ca a ete utile ??                (NOUVEAU — retour/note sur l'utilite
                                        de l'alerte, utile pour detecter les
                                        abus ou ameliorer la confiance)
- messages envoyes

NOTE : correspond a "Alert" + "AlertNotification" + "Message" dans
plan.txt. Deux champs restent vraiment nouveaux et valent la peine d'etre
portes dans plan.txt : la confirmation a posteriori de la personne
concernee, et le retour d'utilite (le motif de l'alerte est deja integre).
