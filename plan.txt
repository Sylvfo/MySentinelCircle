MY SENTINEL CIRCLE — PROJECT PLAN (draft, to be reviewed)
===========================================================

CONCEPT
-------
A mutual safety-net app: each user builds tiered "circles" of trusted people
who watch over them. If a user goes silent, someone can raise an alert —
starting with the closest circle, escalating outward if needed. Works in
reverse too: a third party (e.g. hotel staff, coworker) can alert a person's
circle if something happens to them. Designed to be usable in a real
emergency by people who rarely open the app — SMS-first, minimal friction.

ROLES
-----
- Me          : a registered user; manages their own circles and permissions.
- Companion   : a person "Me" watches over; has an account (a Companion is
                someone else's "Me").
- Sentinel    : a registered person chosen by "Me" to be part of a circle.
                Must explicitly accept the invitation before becoming active
                — "Me" cannot add someone as a Sentinel without their
                validation. Comes in two types (see CIRCLES & PERMISSIONS):
                Sentinel (base) or Sentinel+.
- Organization : (placeholder name, to be finalized) a vetted entity — hotel
                chain, vacation camp, police, school, business, etc. —
                subject to stricter verification than individual users
                (method TBD). Has multiple staff accounts (OrganizationMember)
                who log in on its behalf under internal roles. Once verified,
                logged-in staff can flag a concern about someone with just
                that person's phone number — identified via an authenticated
                API call and restricted to vetted organizations to cut scam 
                risk. Beyond that phone-only alert
                trigger, logging in also opens the door to more rights
                (exact scope TBD — see OPEN POINTS).

CIRCLES & PERMISSIONS
----------------------
- Each "Me" defines multiple circles (e.g. 1st circle/family, work,
  neighbors), ranked by tier. The 1st circle is the "close circle" — it's
  the one that receives the first alert, and only it can escalate outward
  to the other circles. Meant to stay small (roughly 1 to 5 people), since
  during an active alert its members share one live group chat together
  (see Alert lifecycle).
- Independently of circle tier, each Sentinel has a type governing how much
  they can exchange, chosen by "Me" per Sentinel:
    - Sentinel   : quick predefined replies only ("ok vu tel jour",
                   "checker pas vu", etc.) — that's the extent of it, they
                   cannot otherwise communicate with the 1st circle; it's a
                   one-way signal, not a conversation.
    - Sentinel+  : during an active alert, can request to open a dedicated
                   group chat with the 1st circle (text, photos,
                   location/map) instead of the base Sentinel's predefined
                   replies. Each Sentinel+ who requests gets their own
                   separate chat with the 1st circle — not one chat shared
                   across every Sentinel+ (see Alert lifecycle).
  Circle tier (does this Sentinel sit in the 1st circle, and can they
  escalate?) and Sentinel type (Sentinel vs Sentinel+) are two separate
  settings — a Sentinel in the 1st circle isn't necessarily Sentinel+, and
  vice versa.
- The link can be initiated from either side: "Me" can invite someone as a
  Sentinel, or someone can request to become a Sentinel for a given "Me".
  Either way, the party who didn't initiate must validate before the link
  becomes active — invited Sentinels must accept "Me"'s invitation, and
  "Me" must approve incoming Sentinel requests. Only accepted links can
  receive alerts or count toward a circle.
- Organizations bypass circle structure entirely when alerting with just the
  target's phone number, from within the app — the alert always routes to
  the 1st circle first.

CORE FEATURES (MVP)
--------------------
1. Auth
   - Every account requires BOTH an identity credential (email+password OR
     Google account) AND a phone number at signup, verified via OTP. Phone
     is never optional: it's the core assurance to users that the people in
     their circles can actually be reached when an alert fires.
   - Signup/login options: phone + SMS OTP (fast path), email + password,
     or Google OAuth — phone verification is mandatory in all cases, even
     when signing up via Google.
   - Password reset via email link — does not depend on having the phone
     (n/a for accounts that only use Google as their credential).
   - If the phone number changes (lost/replaced device+SIM), the user logs
     in via email+password and updates their phone number from account
     settings; the new number is re-verified via OTP before use in alerts.

2. Circle management
   - Create circles, invite Sentinels/Companions, set per-member permissions
     (escalation rights, Sentinel type).
   - A Sentinel link can start from either side: "Me" invites someone, or
     someone requests to become a Sentinel for a given "Me". Whichever side
     didn't initiate must validate before the link becomes active.
   - Every new Sentinel is assigned to a circle right away — a Sentinel
     always belongs to exactly one circle from the moment the link exists.

3. Alert lifecycle
   - A registered Sentinel raises an alert for the Companion they watch
     over, either in-app or via SMS — never the other way around, a
     Companion never raises an alert about themselves. Either way, a
     reason message (free text describing why the alert is being raised)
     is required before it dispatches.
   - A verified Organization raises an alert from within the app: a logged-in
     OrganizationMember, identified via an authenticated API call rather
     than anonymous SMS, submits the target's phone number plus a reason ->
     1st circle notified immediately -> an in-app chat opens between the
     Organization and the 1st circle for follow-up (see DATA MODEL:
     AlertChat). No prior link between the Organization and the target
     person is required (e.g. a hotel reporting a guest they just found
     injured). Anonymous, non-organization phone-only alerts are no longer
     allowed — judged too easy to abuse for scams.
     MVP scope: ship a small, minimal slice of this first (raise + notify
     1st circle + open chat) — the fuller Organization verification/
     dashboard work (see OPEN POINTS) can follow later; Organizations stay
     in the model even at this stage since they're a potential paying
     customer segment (B2B), not just a nice-to-have.
   - Organization flow: look up the target user by phone number -> notify
     the 1st circle -> open a dedicated Organization<->1st circle chat for
     that alert.
   - The "Me" the alert concerns is also contacted directly (SMS/push) as
     soon as the alert is raised — not just their circle. "Me" can take
     control of the alert at any point (e.g. mark themselves safe / resolve
     it directly), overriding whatever the circle is doing; the circle is
     then notified the alert was closed by "Me".
   - Only 1st circle members or "Me" can close an alert — other circles,
     once escalated to, can respond but not close it themselves. 1st circle
     can also escalate to the next circle if the person can't be reached.
   - Once an alert is active, all 1st circle members share one live group
     chat ("1st circle chat") — that's what keeps the 1st circle
     intentionally small. Sentinels outside the 1st circle can't join this
     chat. A pre-authorized Sentinel+ (see CIRCLES & PERMISSIONS) can
     request, during the alert, to open a separate group chat with the 1st
     circle — each requesting Sentinel+ gets their own isolated chat with
     the 1st circle, not one chat shared across multiple Sentinel+.
   - Notifications go out via SMS (and push, for app users); replies parsed
     automatically (predefined keywords for base Sentinels, free text/media
     for Sentinel+). Predefined reply set for taking an alert:
       - "je vais voir tout de suite"
       - "je peux aller voir à tel moment"
       - "pas dispo, demandez-moi plus tard"
       - "pas dispo"

4. Messagerie Me <-> Sentinels
   - Outside of any active alert, "Me" can message any of their Sentinels
     directly, regardless of Sentinel type — this general messaging isn't
     gated by the Sentinel/Sentinel+ split.
   - The Sentinel/Sentinel+ distinction only restricts communication during
     an active alert (predefined replies vs shared chat) — it doesn't apply
     to this everyday messaging.
   - This messaging is always Me<->Sentinel (1:1). Sentinels never message
     each other directly outside of an active alert. During an active
     alert, several scoped group chats can exist instead (see Alert
     lifecycle): the 1st circle's own group chat between its members; on
     request, a separate chat between one pre-authorized Sentinel+ and the
     1st circle; and, for Organization-raised alerts, a chat between the
     Organization and the 1st circle. All are scoped to that specific
     alert and don't exist outside of it.

5. History / audit trail
   - Per user: full log of alerts raised, who was contacted, who responded
     (and how), and the underlying message history.

DATA MODEL (sketch)
--------------------
- User              : account holder (email, passwordHash, phone), dual auth.
- Contact            : a person known in someone's circles by phone number;
                       optionally linked to a User if they ever register
                       (covers Sentinels without accounts).
- Circle             : belongs to a User, has a tier/rank and a label.
- CircleMembership   : links a Contact to a Circle, with canEscalate,
                       sentinelType (sentinel | sentinel_plus), status
                       (pending | accepted | declined), and initiatedBy
                       (me | sentinel) — tracks whether "Me" sent the
                       invitation or the Sentinel requested the link, since
                       the other party is the one who must validate it.
- Organization       : a vetted entity (hotel, school, police, business...)
                       that can raise phone-only alerts once verified;
                       verification status (pending/verified/rejected) and
                       method TBD.
- OrganizationMember : links a User (staff) to an Organization, with an
                       internal role (e.g. admin, staff) governing what they
                       can do when acting on the Organization's behalf.
- Alert              : raised for a target User, with status
                       (active/escalated/resolved), origin (Sentinel via
                       app | Sentinel via SMS | Organization via app), a
                       required reason (free text, why the alert is being
                       raised — collected up front at creation time for
                       every origin), resolvedBy (target user themselves
                       vs a circle contact).
- AlertNotification  : one row per contact notified for a given alert,
                       including the target User themselves (they're
                       always notified directly, not only their circle);
                       delivery + response tracking.
- AlertChat          : a chat thread scoped to one alert. Three kinds:
                       `circle` (the 1st circle's own group chat — one per
                       alert, open to all 1st circle members), `sentinel_
                       plus` (one per Sentinel+ who requests to talk during
                       the alert, scoped to just that Sentinel+ and the 1st
                       circle), and `organization` (opened automatically
                       when an Organization raises the alert, scoped to
                       that Organization and the 1st circle — no separate
                       request needed, since being a logged-in verified
                       Organization is itself the authorization). Several
                       `sentinel_plus` chats can coexist on the same alert,
                       each isolated from the others; at most one
                       `organization` chat exists per alert. Opening a
                       `sentinel_plus` chat requires both the standing
                       sentinelType = sentinel_plus permission and an
                       in-the-moment request during the alert.
- Message            : full message log (SMS/push), carries a type (text |
                       photo | location); tied either to a specific
                       AlertChat (in-alert conversation) or, when chatId is
                       null, to a standalone Me<->Sentinel conversation
                       outside any alert. During an active alert, base
                       Sentinel replies are limited to a fixed set of
                       predefined texts and aren't part of any AlertChat.
                       Outside of an alert, any Sentinel (base or +) can
                       message "Me" freely.
- EscalationEvent    : records each escalation: from circle -> to circle,
                       who triggered it, when.

BACKEND MODULES (NestJS, sketch)
----------------------------------
- Auth        : login/signup itself — phone+OTP, email+password, Google
                OAuth; issues sessions/JWT. Kept separate from User so auth
                strategies can evolve independently of profile data.
- User        : create/modify account info; read own data (incl. alert
                history); accept/decline incoming Sentinel invitations.
- Sentinel    : register Sentinels (either direction — invite or request),
                define circles, set per-Sentinel rights (sentinelType,
                canEscalate).
- Alert       : send alerts (app + SMS), respond to an alert, notify the
                relevant circles, notify everyone once an alert is closed.
                Enforces that only 1st circle members or "Me" can close it.
- Organization : authenticate the OrganizationMember, look up a target user
                by phone number, raise the alert (with reason), notify the
                1st circle, and open the Organization<->1st circle
                AlertChat for that alert.
- Messaging   : everyday Me<->Sentinel conversations outside of any active
                alert (open to any Sentinel, base or +); also backs the
                in-alert AlertChats used by Alert (the 1st circle's own
                chat, one isolated chat per requesting Sentinel+, and the
                Organization chat for Organization-raised alerts), but the
                two contexts enforce different rules (free-form always
                here vs Sentinel-type-gated and request-based during an
                alert).

TECH STACK (confirmed)
------------------------
- Backend      : NestJS + TypeScript
- Frontend web : React + TypeScript
- Mobile       : React Native
- ORM / DB     : Prisma + PostgreSQL, hosted on Neon (cloud, no local install)
- SMS          : pluggable provider, decide later (Twilio likely default)
- Infra        : no Docker/Nginx for now — run services directly in dev
