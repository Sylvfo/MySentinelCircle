A FAIRE PLUS TARD
===================

Choses reportees pendant l'implementation, a rebrancher quand pretes.

1. SMS OTP — Twilio (ou alternative)
   - Actuellement stub dev : l'OTP est genere et logge en console au lieu
     d'etre envoye par SMS.
   - Code ecrit derriere une interface pluggable (OtpSenderService) pour
     brancher Twilio sans toucher au reste du flow Auth.
   - Il faudra : compte Twilio, Account SID, Auth Token, numero d'envoi,
     -> variables d'env TWILIO_ACCOUNT_SID / TWILIO_AUTH_TOKEN /
     TWILIO_FROM_NUMBER.

2. Google OAuth
   - Flow code cote backend (strategie passport-google-oauth20) mais pas
     fonctionnel tant que les identifiants ne sont pas crees.
   - A faire : creer un projet sur Google Cloud Console, activer l'OAuth
     consent screen, creer un Client ID/Secret OAuth 2.0 (type "Web
     application"), ajouter les redirect URIs.
   - -> variables d'env GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET /
     GOOGLE_CALLBACK_URL.

3. Reset de mot de passe par email
   - Fonctionnalite entierement reportee (pas codee dans cette passe
     d'Auth) : signup/login (phone+OTP, email+password, Google) et JWT
     d'abord.
   - Il faudra choisir un provider d'envoi d'email (Resend, SendGrid,
     Postmark...) puis coder l'endpoint de demande de reset + lien a
     usage unique + page/flow de saisie du nouveau mot de passe.

4. Internationalisation (i18n) — site multilingue
   - FAIT (front) : react-i18next branche, FR + EN, defaut FR, detection
     navigateur + memorisation localStorage, selecteur de langue. Textes
     UI dans frontend/src/i18n/locales/{fr,en}.json.
   - RESTE : backend — messages d'erreur/validation renvoyes en dur (ex.
     "Code invalide" cote API). Si on veut les afficher tels quels cote
     client, les traduire via header Accept-Language. Pour l'instant le
     front a ses propres messages de fallback traduits, donc non bloquant.
   - Penser a ajouter les cles i18n au fur et a mesure des nouveaux
     modules (Sentinel, Alert, Messaging) plutot que du texte en dur.

5. Divers (deja notes dans plan.txt sous OPEN POINTS, rappeles ici)
   - Taille du 1er cercle (1 a 5 personnes) : cap dur ou juste indicatif ?
   - Nom final de la categorie "Organization".
   - Mecanisme de verification des Organizations (revue manuelle, check
     registre d'entreprises, domaine email pro...).
   - Roles internes Organization (admin vs staff) : perimetre exact.
   - Perimetre exact de ce qu'un staff Organization peut faire au-dela de
     lever une alerte phone-only (dashboard, historique, plusieurs alertes
     en cours...).
   - Check-ins programmes (explicitement hors MVP).
   - Notifications push en plus des SMS pour les users de l'app.
